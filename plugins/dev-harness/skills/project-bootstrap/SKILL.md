# project-bootstrap — 프로젝트에 하네스 적용

훅(.bak 차단·py_compile·세션 기록)은 플러그인이 켜져 있으면 이미 동작한다.
이 스킬은 **프로젝트 고유 지식을 담는 파일**을 만드는 절차다.

## 0. 먼저 모드를 정한다

`ls` 로 루트를 훑고, 어느 모드로 진행하는지 사용자에게 한 줄로 알린 뒤 시작한다.

| 모드 | 조건 | 절차 |
|------|------|------|
| **A. 기존 소스** | 소스·설정 파일이 있다 | §1 → §3 |
| **B. 신규 착수** | 폴더가 비었거나 기획·설계 문서만 있다 | §2 → §3 |

판단이 애매하면(문서만 있고 코드가 없다) **B** 다.
B 인데 A 절차를 돌리면 `(확인 필요)` 만 가득한 CLAUDE.md 가 나온다 — 그건 실패다.
그럴 때는 문서를 만들지 말고 §2 로 넘어간다.

---

## 1. 모드 A — 기존 소스에서 뽑아내기

`ls` 와 주요 설정 파일(`package.json`, `requirements.txt`, `docker-compose.yml`,
`pyproject.toml`, `*.csproj`, `deploy*.sh`, CI 워크플로우 등)을 읽어 다음을 파악한다.

- 서비스 개요(무엇을 하는 시스템인지 한 문단)
- 소스 루트와 git 저장소 위치(프로젝트 폴더 = 저장소인지, 하위 폴더인지)
- 기술 스택과 의존성 파일 위치
- 배포 방식(스크립트·CI·수동)과 시크릿 파일(gitignore 대상)
- 테스트/검증 명령과 **성공 기준**(무엇이 통과하면 끝인지 — 테스트·헬스체크·재현 스크립트)
- **이미 기계로 강제되는 규칙**(린터 설정, CI 잡, import 금지 규칙) — CLAUDE.md 5절에 그대로 옮긴다

읽어서 알 수 없는 것은 추측해 적지 말고 `(확인 필요)` 로 남긴다.

---

## 2. 모드 B — 신규 프로젝트 착수 순서

**코드부터 쓰지 않는다.** 문서 → 계획 → 사람 리뷰 → 단계별 구현 순서를 지킨다.
각 단계를 사용자와 합의하며 진행하고, 사용자가 이미 끝낸 단계는 건너뛴다.

### 2.1 입력 문서를 `docs/baseline/` 에 모은다
기획서·발표자료·요구사항 등 판단의 근거가 되는 원본. 이후 모든 지시는 이 폴더를 가리킨다.
넣을 문서가 없으면 사용자에게 무엇이 있는지 먼저 묻는다 — **없이 계획을 세우지 않는다.**

### 2.2 코딩 스탠다드를 **가장 먼저** 만든다 — `docs/standard/`
프론트엔드·백엔드로 나눠 중복 없이 정리한다. 이후 "이 기준으로 리팩토링해줘" 의 근거가 되므로
계획서보다 먼저 존재해야 한다. 규모가 크면 별도 워크트리에서 병렬로 작성한다.

### 2.3 비기능 요구사항을 **숫자로** 확정한다
동시 접속 수, 총 사용자 수, 응답 시간, 데이터 규모. 모르면 사용자에게 묻는다.
숫자가 없으면 과설계가 나온다(1,000명 가정 → 실제 10명 같은 차이가 아키텍처를 바꾼다).

### 2.4 계획을 먼저 세운다 — `docs/plan/`, **이 단계에서 코드는 쓰지 않는다**
`docs/baseline` 과 `docs/standard` 를 근거로 아래를 담은 계획서를 쓴다.
- 기술 스택(BE/FE/DB)과 컨테이너 분리 구성, 설정은 환경변수로 주입
- 도메인 로직은 DB·외부 API를 직접 호출하지 않고 **인터페이스에만 의존**, 구현체는 주입
  (인메모리 구현으로 단위 테스트 가능하게 — 이게 "사람이 코드를 덜 봐도 되는" 근거가 된다)
- 테스트 unit / integration / E2E 분리 실행
- 인증·인가는 라우터와 분리, 모든 관리자 기능에 인가 필수
- 레이어 규칙을 **CI 에서 강제**한다는 명시
- 단계별 구현 계획, 데이터 모델 초안
- 기획서에서 불명확하거나 외부 결정이 필요한 사항 목록

### 2.5 계획서를 사람이 한 줄씩 리뷰한다
Claude 는 "리뷰해 주세요" 로 넘기지 말고 **쟁점을 목록으로 뽑아** 제시한다
(해석이 갈리는 용어, 정원·버퍼 같은 수치 해석, 인증 방식, 데이터 모델).
가능하면 기획 담당까지 함께 보게 안내한다 — 혼자 읽을 때 놓치는 것이 여기서 잡힌다.

### 2.6 결정이 필요한 사항은 분리한다 — `docs/decisions/`
외부 의존(연동 리드타임, 파일 포맷), 미결 정책은 계획서에 섞지 말고 별도 문서로 빼서
commit 을 요청한다. 결정되면 그 문서를 갱신하고 계획서에 반영한다.

### 2.7 단계를 끊어 구현한다
"0단계만" 처럼 범위를 명시해 지시받고, 한 단계가 끝나면 멈추고 보고한다.
0단계(바닥)의 표준 구성: CI, 컨테이너, 디자인 토큰·프리미티브, 인증 화면, 감사로그 뼈대.
**전체를 한 번에 구현하지 않는다.**

### 2.8 아키텍처 규칙은 문서가 아니라 CI 로 강제한다
"domain 에서 ORM import 금지", "모든 use case 에 인가 데코레이터" 같은 규칙은
린터·테스트·CI 잡으로 만들어 어기면 빌드가 깨지게 한다. 강제 수단이 생길 때마다
CLAUDE.md 5절 표에 기록한다. **프롬프트는 잊히지만 CI 는 잊지 않는다.**

## 3. 공통 — 하네스 파일 생성

### 3.1 CLAUDE.md
루트에 이미 있으면 **덮어쓰지 않는다.** 빠진 섹션만 제안하고 멈춘다.
없으면 `templates/CLAUDE.md.tmpl` (이 플러그인 폴더의 `templates/`) 을 읽어 `{{...}}` 를 채운다.
- 모드 A: §1 에서 파악한 내용으로
- 모드 B: 2.1~2.4 의 결과물 경로와 확정된 숫자로. 아직 없는 항목은 `(미정 — 2.x 단계)` 로 남긴다
모르는 항목은 지우지 말고 `(확인 필요)` 로 남겨 사용자가 채우게 한다.
백서·설계문서가 있으면 "원본 근거" 에 경로를 적는다.

### 3.2 `.claude/verify.toml` (Python 코드가 있을 때)
```toml
[verify]
repo              = "."                 # git 저장소가 하위 폴더면 그 이름
requirements_dirs = []                  # requirements.txt 가 있는 디렉터리 (repo 기준). 컨테이너 배포면 꼭 채운다
env_known_files   = ["CLAUDE.md", ".env"]
env_hint          = "배포 환경 .env 수동 추가 필요 여부 확인"
```
서비스별 컨테이너로 나뉘면 `requirements_dirs` 에 **서비스 디렉터리를 각각** 적는다.
verify.py 는 Python 만 본다 — 프론트엔드 lint/test 명령은 CLAUDE.md 0절 "검증 명령" 에 적어
누락되지 않게 한다.

### 3.3 `.claude/skills/`
폴더를 만들고 첫 스킬 후보를 안내한다. CLAUDE.md 가 길어질 항목(환경변수 실측값, 배포 트리거 표,
버전 이력)은 처음부터 `.claude/skills/<프로젝트약칭>-env/SKILL.md` 식으로 분리한다.
SKILL.md 는 frontmatter 의 `name` 과 `description` 이 필수이며, description 에 "언제 사용" 을 반드시 적는다.

### 3.4 마무리
verify 를 1회 실행해 설정이 맞는지 확인하고, 만든 파일 목록과 사용자가 채워야 할
`(확인 필요)` / `(미정)` 항목을 보고한다. 모드 B 면 **다음에 할 단계**를 한 줄로 덧붙인다.

## 원칙

- CLAUDE.md 에는 **"어디를 봐야 하는지"와 "지켜야 하는 규약"** 만 압축해 둔다.
  코드로 알 수 있는 것(디렉터리 목록, 함수 시그니처)은 적지 않는다.
- 공통 규약(워크플로우·.bak 금지·env 플래그)과 **코드 작성 태도 4원칙**(생각 먼저·단순함·외과적
  변경·목표 기반)은 `harness-workflow` 스킬에 있으므로 CLAUDE.md 에는 참조 한 줄만 두고
  중복 기술하지 않는다. CLAUDE.md 5절에는 **이 프로젝트에서만 성립하는 규약**만 적는다.
- 부트스트랩 자체도 외과적으로 한다. 기존 파일을 재작성하지 말고 빠진 섹션만 덧붙인다.
- 상대 날짜는 절대 날짜로 적는다.
- **초반에 빡빡하게 볼수록 나중에 덜 본다.** 레포 초기 세팅과 인증 코드는 사용자에게
  한 줄씩 검증을 권하고, 그 대신 DB 없이 도는 단위 테스트를 촘촘히 깔아 이후 검증 부담을 줄인다.
- 독립적으로 진행 가능한 작업(코딩 스탠다드 작성 등)은 **워크트리 분리**를 제안한다.
- 모르는 용어가 나오면 넘기지 말고 그 자리에서 설명하거나 사용자에게 묻는다.
