# harness-workflow — 공통 작업 규약

이 규약은 dev-harness 플러그인이 켜진 모든 프로젝트에 적용된다. 프로젝트별 세부(배포 경로,
환경변수, 알려진 함정)는 각 프로젝트의 `CLAUDE.md` 와 `.claude/skills/` 가 우선한다.

## 1. 워크플로우

```
[Claude]  요청 분석 → 로컬 소스 수정
   ↓
[Claude]  verify.py 자가 검증 실행 → 결과 보고 (+ 변경 요약·검증 포인트 제시)
   ↓
[사용자]  로컬에서 확인 → git commit & push
   ↓
[서버/CI] 프로젝트별 배포 절차 (CLAUDE.md 참조)
```

- **git 커밋·푸시·배포는 사용자가 한다.** Claude 는 파일 수정까지만 하고, 커밋 메시지 초안과
  배포 시 영향 범위·검증 방법을 함께 안내한다. git 은 읽기 명령(status/diff/log)까지만 쓴다.
- 수정 후에는 **어떤 파일 / 어떤 함수 / 왜** 를 요약한다.

## 2. 자가 검증 (verify)

수정이 끝나면 커밋을 요청하기 전에 반드시 실행한다.

```
python "C:\Users\user\claude-harness\plugins\dev-harness\scripts\verify.py" --root "<프로젝트 루트>"
```

- 검사: ① 변경 .py py_compile ② requirements.txt ↔ import 대조(설정 시) ③ .bak 감지 ④ 신규 env 키 경고.
- 프로젝트 설정은 `<루트>/.claude/verify.toml` (없으면 기본 검사만). 형식은 verify.py 상단 docstring 참조.
- 종료코드 0 = PASS. 경고는 통과지만 반드시 사용자에게 전달한다(특히 신규 env 키).

## 3. 기계적으로 강제되는 규약 (훅)

- **`.bak` 백업 파일 생성 금지** — Write/Edit 의 파일명, Bash/PowerShell 의 복사·이동·리다이렉트 명령을
  훅이 차단한다. 롤백은 git 히스토리로 하고, 변경 전후 diff 를 요약해 보고한다.
- **`.py` 저장 직후 py_compile** — 문법 오류가 있으면 훅이 즉시 피드백한다. 그 자리에서 고친다.
- **세션 종료 시 대화 기록 저장** — `~/claude-logs/sessions/<프로젝트 폴더명>/` 에 md 로 저장·커밋된다
  (민감정보 마스킹). 저장 위치는 `CLAUDE_HARNESS_LOG_DIR` 환경변수로 바꿀 수 있다.

## 4. 코드 작성 태도

출처: Karpathy 의 LLM 코딩 실패 패턴 관찰을 정리한 `multica-ai/andrej-karpathy-skills` (MIT).
**속도보다 신중함 쪽으로 치우친 원칙이다. 사소한 작업에는 판단으로 생략한다.**

1. **짓기 전에 생각한다.** 가정은 말로 꺼낸다. 해석이 갈리면 고르지 말고 나열한다.
   더 단순한 방법이 보이면 말한다. 헷갈리면 멈추고 무엇이 헷갈리는지 이름을 붙여 묻는다.
2. **단순함이 먼저.** 요청 범위 밖 기능, 1회용 코드의 추상화, 요청하지 않은 설정 가능성,
   일어날 수 없는 상황의 예외 처리를 넣지 않는다. 200줄이 50줄이면 되는지 되돌아본다.
3. **외과적 변경.** 바꿔야 할 곳만 바꾼다. 주변 코드·주석·포맷을 "개선" 하지 않고,
   내 취향과 달라도 기존 스타일을 따른다. 무관한 죽은 코드는 **지우지 말고 보고**한다.
   단, **내 변경이 만들어 낸** 미사용 import·변수·함수는 내가 치운다.
   판정 기준: 바뀐 모든 줄이 사용자의 요청으로 곧장 추적되는가.
4. **목표 기반 실행.** 작업을 검증 가능한 목표로 바꾼 뒤 통과할 때까지 스스로 돈다.
   "검증 추가" → "잘못된 입력의 테스트를 쓰고 통과시킨다",
   "버그 수정" → "재현 테스트를 먼저 쓰고 통과시킨다". 다단계 작업은 착수 전에
   `단계 → 확인 방법` 형태로 짧은 계획을 밝힌다. §2 의 verify 는 이 확인의 최소 하한선이지
   성공 기준 자체가 아니다 — 프로젝트의 성공 기준은 CLAUDE.md 0절에 적는다.

## 5. 코드 수정 시 지킬 규약

1. **env 플래그 + 기본 보수값** — 신규 기능은 `*_ENABLED` 류 환경변수로 감싸고, off 시 이전 동작과
   100% 동일(회귀 0)하게 만든다.
2. **신규 환경변수는 코드 push 만으로 반영되지 않는다** — `.env` 류는 보통 gitignore 대상이다.
   env 를 추가하면 배포 환경에 수동 추가가 필요하다는 사실을 반드시 함께 안내한다.
3. **공용 헬퍼 단일화** — 같은 규칙을 여러 경로가 쓰면 헬퍼로 묶어 드리프트를 막는다.
4. **대형 단일 파일은 해당 함수 범위만 편집**하고 전체 재작성은 하지 않는다(§4-3 의 구체화).
5. **모듈 레벨 import 누락 주의** — 지연 사용 모듈도 상단 import 를 확인한다.
6. 한글 문자열 비교 코드를 새로 쓸 때는 NFC 정규화부터 한다.

## 6. 수정 보고 형식

- 변경 파일·함수·이유 요약
- verify 결과 (PASS/FAIL, 경고 내용)
- 커밋 메시지 초안
- 배포 시 영향(재빌드/재시작/정적 등, 프로젝트 CLAUDE.md 기준)과 검증 방법
- 신규 env 키가 있으면 "배포 환경 .env 수동 추가 필요" 명시
